# Отчёт по лабораторной работе 3

Тема: разработка стайлгайда на разработку и оформление документации.

Цель: освоить цикл Docs as Code на примере документации программного
обеспечения для преобразования рукописного текста в машинописный.

## 1 Теоретическая основа

Стайлгайд — согласованный набор правил, который определяет структуру,
язык, терминологию, оформление и проверку документации. В Docs as Code
исходники документов хранят вместе с конфигурацией сборки в Git, изменения
обсуждают через Pull Request, а проверки и публикацию автоматизируют.
Это делает изменения прослеживаемыми: можно определить автора, причину
правки и версию, в которой она появилась.

Изучены открытые материалы Google о техническом письме, документация MkDocs,
markdownlint-cli2, GitHub Pages и спецификация Conventional Commits.
Перечень приведён в [источниках](docs/sources.md).
Презентация, упомянутая в условии, в предоставленной папке отсутствовала.

## 2 Ответы на вопросы

### Нужны ли стайлгайды и всегда ли они необходимы

Стайлгайды нужны, когда согласованность текста влияет на понимание продукта,
а над документацией работают несколько авторов. Например, если одна и та же
операция названа «распознаванием», «конвертацией» и «оцифровкой», читатель
может принять её за три разных функции. Единый термин устраняет эту неоднозначность.
Общие шаблоны также уменьшают число повторяющихся замечаний при ревью.

Объём правил должен соответствовать масштабу проекта. Для одноразового
прототипа достаточно краткой памятки. Для развивающегося продукта нужны
правила структуры, терминологии, ошибок, доступности и актуализации.
Избыточные правила, которые нельзя проверить или объяснить задачей читателя,
увеличивают стоимость сопровождения. Поэтому стайлгайд следует расширять
по реальным проблемам документации.

### Как использовать стайлгайд при разработке документации

До написания текста автор выбирает шаблон и аудиторию. Во время работы
использует словарь и правила оформления. Перед публикацией проверяет
документ по чек-листу и запускает автоматические проверки. Рецензент
ссылается на идентификатор правила вместо субъективного замечания.

Примеры применения: инструкция по распознаванию содержит предварительные
условия и ожидаемый результат по S01; названия кнопок выделены по F05;
термин «распознанный текст» используется по T01; метрики качества описаны
с нормализацией и знаменателем по Q03 и Q04. Если меняется формат экспорта,
по G04 вместе с продуктом обновляют соответствующую инструкцию.

### Как использовать искусственный интеллект при разработке стайлгайда

ИИ можно использовать для поиска непоследовательной терминологии,
предложения структуры, подготовки черновиков примеров и сравнения текста
с правилами. Например, проверка по T01 выявляет «юзер» вместо «пользователь»,
а проверка по S01 показывает отсутствие ожидаемого результата в инструкции.
ИИ также может сгруппировать повторяющиеся замечания ревью и предложить
новое правило.

Автор должен проверять предложения по спецификации и примерам. ИИ может
ошибочно придумать кнопку, ограничение формата или результат теста.
Поэтому формальные нарушения проверяет линтер, факты и пригодность текста
оценивает человек, а реальные результаты испытаний фиксируют по выполненным тестам.
Закрытые рукописи и персональные данные не передают внешнему сервису без разрешения.

## 3 Объект разработки

Объект — техническая документация системы автоматического преобразования
рукописного текста в машинописный. Аудитории: пользователи, разработчики,
тестировщики и сопровождающие. Пользовательская документация охватывает
загрузку изображения, распознавание, исправление и экспорт; техническая —
ограничения, интерфейсы при их наличии и воспроизводимые проверки качества.

## 4 Разработка стайлгайда

### 4.1 Структура правил

| Раздел | Вопросы, на которые отвечают правила |
| --- | --- |
| Общие положения | Для кого написан документ, к какой версии относится, кто отвечает за актуальность |
| Структура документации | Какие разделы обязательны для инструкции, описания компонента и протокола |
| Язык и стиль | Как формулировать действия, условия и проверяемые утверждения |
| Терминология | Какие названия едины, как раскрывать сокращения |
| Форматирование | Как оформлять Markdown, списки, таблицы, код, изображения и ссылки |
| Описание функциональности | Как описывать вход, действие и результат пользовательской операции |
| Ошибки и ограничения | Как разделять симптом, причину, действие и границы поддержки |
| Тестирование | Как фиксировать данные, нормализацию, результаты и метрики |
| Доступность текста | Как сделать структуру, ссылки и изображения понятными разным читателям |

### 4.2 Правила

Правила сформулированы как проверяемые требования с идентификаторами:
G — общие положения, S — структура, L — язык, T — терминология,
F — форматирование, D — функции, E — ошибки, Q — тестирование,
A — доступность. Для требований используются слова «должен» и «нельзя»,
для рекомендаций — «рекомендуется». Порядок исключений определён на главной странице.

Восемь основных разделов содержат 38 нумерованных правил. Раздел доступности
добавляется отдельной веткой и PR по пункту 11 задания.
Полный текст правил находится в [руководстве](docs/index.md).

### 4.3 Структура стайлгайда

Руководство организовано как сайт: вводная страница; разделы основных правил;
раздел доступности в отдельном PR; примеры применения; оценка качества;
источники. Навигация задаётся в `mkdocs.yml`. В корне репозитория размещены
`README.md`, `CONTRIBUTING.md`, настоящий отчёт и настройки инструментов.

### 4.4 Фиксация правил

Каждый раздел хранится отдельным Markdown-файлом в `docs/guide/`.
Это позволяет обсуждать конкретную правку, просматривать историю
и повторно использовать правила через ссылки. Изменения проходят линтинг,
строгую сборку MkDocs и содержательное ревью.

## 5 Апробация и оценка

По разработанным правилам составлены два документа:

1. [Инструкция U01](docs/examples/user-guide.md): от загрузки изображения
   до проверки экспортированного файла.
2. [Протокол T01](docs/examples/test-protocol.md): расчёт CER и WER
   для эталона `мама мыла раму` и результата `мама мыла рамы`.

В T01 одна символьная замена при длине эталона 13 даёт CER = 1 / 13 × 100 =
7,69 %. Одна замена слова среди трёх даёт WER = 1 / 3 × 100 = 33,33 %.
Пробелы входят в символьную длину, конечный перенос строки исключён.
Пример проверяет расчёт и описание процедуры, а не точность работающей модели.

Апробация выявила необходимость уточнить область применения примеров,
нормализацию метрик и проверку экспортированного файла. Эти уточнения
включены в G02, Q04 и D05. В результате оба документа проходят шесть
применимых содержательных критериев. Подробности и ограничения оценки
приведены в [матрице проверки](docs/evaluation.md).

## 7 и 8 Настройка MkDocs и разделов

Используется MkDocs 1.6.1. Файл `mkdocs.yml` задаёт русскую локализацию,
поиск, адрес сайта, ссылку на исходники и явную навигацию по всем страницам.
Режим `strict` превращает предупреждения сборки в ошибки. Разделы правил
и оба примера заполнены содержательным текстом.

## 9 Настройка линтинга

Используется markdownlint-cli2. Версия фиксируется в `package.json`,
дерево зависимостей — в `package-lock.json`. Конфигурация
`.markdownlint-cli2.jsonc` проверяет Markdown в репозитории и исключает
зависимости и результат сборки. Ограничение длины строки отключено,
поскольку длинные русские абзацы и таблицы удобнее переносить редактором.
Линтер не проверяет достоверность содержания и все правила естественного языка.

## 10 Настройка CI/CD

Workflow `.github/workflows/docs.yml` выполняется для PR и коммитов в `main`.
Задание `check` устанавливает зависимости, запускает линтер и строгую сборку.
Для `main` собранный сайт передаётся в Pages; `deploy` зависит от успешного
`check` и публикует этот артефакт. Для PR публикация не запускается.
Права записи Pages предоставлены только заданию публикации.

В настройках GitHub Pages необходимо выбрать источник GitHub Actions.
Результат запуска Actions и доступность сайта проверяются отдельно:
наличие workflow само по себе не подтверждает состоявшийся деплой.

## 11 Ветки и Pull Request

Для нового раздела предусмотрена ветка `codex/text-accessibility`.
В ней добавляются правила доступности и пункт навигации. Коммит следует
Conventional Commits. PR направляется в `main` для независимого ревью.

Ссылка на PR партнёра пользователем не предоставлена. Поэтому обмен ссылками,
три комментария к чужому PR и правки по полученным замечаниям остаются
внешними этапами работы. Самостоятельная проверка не считается взаимным ревью.
Слияние раздела доступности следует выполнить после одобрения партнёра.

Разработаны единые правила для документации системы распознавания рукописного
текста и проверено их применение на двух документах. Markdown, Git,
MkDocs и автоматические проверки образуют воспроизводимый процесс
подготовки документации. Содержательное ревью дополняет формальные проверки
и необходимо для проверки достоверности и понятности текста.
